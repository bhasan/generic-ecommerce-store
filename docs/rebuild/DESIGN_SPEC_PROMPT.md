# Prompt: Design Specification for the Multi-Tenant Commerce Platform Rebuild

> Give this entire document as the opening prompt to an AI agent opened inside this repository.
> The agent's deliverable is a design specification, not code.

---

You are a principal software architect. Your mission is to produce a complete, decision-grade **design specification** for a ground-up rebuild of the ecommerce platform in this repository. The rebuild is a **greenfield codebase** — this repo is your behavioral reference, your data-migration source, and your catalog of mistakes to not repeat. You are designing, not implementing: produce no application code beyond illustrative snippets inside the spec.

Work through the five phases in "How to work" below, in order. Checkpoints — the end of Phase 1, the end of Phase 2, and the §4/§9 check-ins in Phase 3 — all mean the same thing: post your output, end your turn, and wait for the product owner's reply before continuing.

## Product vision

The current app is a single company's store retrofitted into a multi-tenant SaaS. The rebuild inverts that: a **multi-tenant commerce platform for independent merchants** — a merchant signs up (or is provisioned), gets one or more storefronts (Tenant → Store hierarchy stays), operates their catalog/orders/staff/integrations in isolation, and reaches customers on their own subdomain or custom domain. Think "focused, self-hostable mini-Shopify for delivery-oriented local retail," not a marketplace: tenants never share customers, catalogs, or data.

Three qualities define success, in priority order:

1. **Tenant isolation you can prove.** Isolation enforced at the database layer, not by convention in application code. A tenant's data must be unreachable from another tenant's context even in the presence of an application bug.
2. **A beautiful, tenant-customizable UI.** The storefront must look professionally designed out of the box, and each tenant must be able to make it *theirs* through a full **theming engine** (defined below) — without a designer and without breaking the design.
3. **Software design worth keeping.** Clear module boundaries, one way to do each thing, horizontal scalability, and the structural prevention of the failure catalog below.

**Non-goals:** a freeform drag-and-drop page builder (section-based configuration only); a marketplace/shared-customer model; preserving the current codebase (only its behavior and data).

## Hard constraints

- **PostgreSQL stays** as the system of record. Everything else — language, framework, frontend stack, monorepo layout, infra — is yours to propose and justify in Phase 2.
- **Feature parity is the floor** (see the inventory below). Dropping or deferring live behavior requires product-owner sign-off — raise it in Phase 1 or at a Phase 3 check-in; the parity matrix records the decision, it does not make it. The dormant features listed below are Phase 1 questions.
- **A migration path must exist** from the current production Postgres schema and uploaded assets to the new system, specified in its own chapter.
- The platform must run economically at small scale (it deploys to a single VPS today) while having a credible path to multi-node scale. No mandatory managed-cloud dependencies.
- Prefer boring, proven technology; every novel choice needs a justification and an exit strategy.

## The system you are replacing

Verify all of this against the code in Phase 0 — treat the repo as the source of truth if anything has drifted.

**Shape:** Express 4 + TypeScript + Prisma 6 / Postgres 16 monolith (`backend/`, routes → controllers → services), React 19 + Vite SPA (`web/`, plain JSX, 71 global CSS files), nginx + Docker Compose on a single VPS, Playwright e2e, Prometheus/Loki monitoring. Multi-tenancy was retrofitted in June 2026 (Phase 1 foundation + Phase 2 multi-store; see `docs/guides/multi-tenancy.md`, `docs/superpowers/specs/2026-06-27-multi-tenancy-foundation-design.md`, `CLAUDE.md`).

**Tenancy today:** shared schema; `tenantId` on every business table, `storeId` additionally on ten store-scoped tables (declared in `backend/src/config/tenantScope.ts`). Isolation is enforced entirely in the application layer: `resolveTenant` middleware (`backend/src/middleware/tenant.middleware.ts`) resolves tenant via priority chain (X-Tenant-ID/X-Tenant-Slug headers → `admin.` subdomain = super-admin scope → host subdomain/`Tenant.customDomain` → JWT claim → default tenant slug `app`), stores context in AsyncLocalStorage, and a Prisma `$extends` interceptor (`backend/src/config/database.ts`) injects tenant/store filters into every query, rewriting `findUnique`→`findFirst`. JWTs are tenant-bound; machine tokens (reporting API, thermal-print agents) identify the tenant by hash. There is **no Postgres RLS backstop**. Five tables are deliberately unscoped and shared across tenants (roles, tenants, stores, refresh_tokens, and address_geocode_cache — the last shares normalized customer-address PII cross-tenant by design; the rebuild must enumerate and justify every shared table under its isolation model). Two different `storeId = 0` sentinels coexist (request-context "all stores" aggregate vs. tenant-default settings row). Per-store catalog values resolve through `StoreVariantOverride` (`backend/src/services/storeVariant.effective.ts`).

**Customization today:** five per-tenant `UiSetting` JSON keys behind a cached `SettingsStore` (`backend/src/services/settingsStore.ts`): `branding` (name, tagline, logo, hero, favicons, 8 preset palettes or custom primary/secondary with server-derived hover/active/light/dark variants, served as CSS custom properties at `/api/branding/css` and raced into first paint by `web/src/main.jsx`), `landing_page_settings` (≤12 featured products, ≤20 promotion slides), `store_settings` (per-store, field-wise inheritance from a tenant-default row), `ordering_constraints`, `payment_settings`. The SPA has a CSS-variable token base (`web/src/styles/theme.css`) with light/dark. **Not customizable:** fonts, layout/sections, per-store branding; some tenant identity is hardcoded in the bundle (`web/src/features/help/HelpPage.jsx` phone number, `web/src/features/products/productsHelpers.js` fallback image).

**Compliance posture (easy to miss, load-bearing):** there is no age-verification code. Instead the entire catalog and store API are **login-gated**, and registration creates unapproved accounts that cannot log in until staff approve them after an in-person ID check (`approved`/`rejected` flags, rejection notes, approval auto-assigns CUSTOMER role). This is the smoke-shop compliance model. The rebuild must treat "who may see and buy" as a first-class, per-tenant policy decision, not an accident of routing.

**Roles:** GUEST (a seeded role backing a client-side anonymous sentinel — see dormant features), CUSTOMER, VIP (unlocks `vipOnly` products), EMPLOYEE, MANAGEMENT, ADMIN (tenant scope, store-scopable via `UserRole.storeId`), DELIVERY_DRIVER (transition-restricted server-side, but see failure #11 for its data over-grant), SUPER_ADMIN (platform scope, currently bolted inside the tenant admin UI).

## Feature inventory to preserve

Orientation only — **your spec must contain a feature-parity matrix built by reading the code**, mapping every current behavior to keep / change / drop / defer with rationale. Every matrix row must cite the source file(s) where the behavior lives; rows citing only this brief do not count. Domains and standouts:

- **Catalog:** hierarchical categories; products requiring ≥1 variant; variant `pricingMode` UNIT or WEIGHT (Decimal(12,3) stock); per-variant quantity-option whitelists (fractional weights); tiered price breaks (largest `minQuantity` ≤ qty wins); exactly-one-default-variant invariant; `hidden`/`vipOnly` visibility (404-not-403 semantics); image roles (thumbnail/gallery) + sort orders; per-product `cardSize` grid presentation; slug/SKU auto-generation; soft-deactivation of ordered variants; CSV import; ZIP catalog export; Postgres FTS + client-side fuse.js search.
- **Per-store commerce:** `StoreVariantOverride` effective price/stock/active resolution (flat price override deliberately suppresses tenant price breaks); admin base-scope editing (`?scope=base`) so saves never persist store-effective values; store clone-from-default seeding; store lifecycle guards (default store must stay ACTIVE; suspended store can't become default).
- **Cart & checkout:** per-store localStorage carts with TTL, legacy migration, and synchronous wipe on session expiry (shared-browser/kiosk safety); quantity stepping through allowed tiers; minimum-delivery-order and delivery kill-switch messaging; tax snapshotted per order (currently a hardcoded 8.25% — must become per-tenant/store config); atomic guarded stock decrement in the checkout transaction; order items snapshot name/label/price at purchase.
- **Payments (strategy registry):** EXTERNAL (CashApp/Zelle/Venmo handles, staff settle on approve, customer-cancel deletes the pending order and restores cart); STORE_CREDIT (tenant-wide ledger with ADDED/REMOVED/USED/REFUNDED entries, `balanceAfter`, reconciliation audit, authoritative balance check in-transaction); IN_STORE (pickup/curbside only); CC via Authorize.Net hosted Accept page (order starts PENDING_PAYMENT with deferred side effects, server-side transaction verification with amount/invoice binding, `transactionId` uniqueness as replay protection — currently unique *globally across tenants*, a coupling the rebuild should scope per tenant/gateway; per-tenant encrypted credentials; sandbox toggle). Abandoned PENDING_PAYMENT orders hold their decremented stock forever (no expiry/reaper exists) — the rebuild needs a payment-session timeout that releases inventory.
- **Fulfillment (strategy registry):** DELIVERY (structured address → minimum-order check → geocoded zone eligibility via Google + shared normalized cache, haversine radius per store settings, failure-taxonomy-driven ZIP fallback, eligibility snapshotted onto the order and cached on the user, live pre-checkout eligibility endpoint); PICKUP; CURBSIDE (vehicle description and parking spot are structured order fields; check-in additionally appends a redundant "| SPOT: …" onto the deliveryAddress string — drop the concatenation).
- **Order lifecycle:** ten statuses across delivery and pickup branches (PENDING_PAYMENT → PENDING → APPROVED / NOT_FULFILLING → READY_FOR_* → … → DELIVERED / PICKED_UP, ARRIVED for curbside); every transition writes an `OrderStatusEvent` audit row in-transaction. The transition graph is enforced only in the staff UI — server-side, any EMPLOYEE+ can set any status from any status (only DELIVERY_DRIVER is restricted; see failure #11). Cancellation today is hard deletion: it cascades away the status-event audit trail, there is no CANCELLED terminal state (the POS status map even maps one that can never fire), and staff can hard-delete DELIVERED orders — the rebuild must model cancellation/rejection as designed states with compensating inventory/financial effects (see failure #4), reserving deletion for admin data hygiene at most. Customer self-cancel only while PENDING; staff add/void/delete items with re-resolved store pricing (money/inventory defects: see failure #4); kanban staff board with deep-linkable status filters.
- **Delivery ops:** driver dashboard with ready-for-delivery / out-for-delivery boards and a staff-built route of ≤5 orders — routes exist only as frontend selection state, with no persisted driver assignment, route entity, or handoff record; the spec must decide whether assignments/routes become modeled domain objects.
- **Identity & access:** username auth — users have **no email field**, and no password-reset/account-recovery flow exists anywhere (coherent for the in-person model; an open decision for a merchant SaaS — Phase 1 question); JWT + rotating refresh tokens (httpOnly cookie, single-flight refresh in the SPA client); registration approval workflow (the applicant's address is geocoded at signup, failing open to UNVERIFIED, and the delivery-zone result is surfaced in the approval queue as staff decision input) with in-app + webhook notifications; store-scoped role assignment UI; per-store staff visibility.
- **Notifications:** seven event types with fixed role fan-out and deep-link paths; `requiresAttention` urgent UX (badge, red dot, one-time WebAudio staff sound with autoplay compliance); per-row delivery status; Make.com webhook contract (README) with per-category URL fallback chain and sanitized payloads; ops-alert email routing/dedup via per-store notification emails; 60s polling (a rebuild should propose push).
- **Printing:** thermal receipt pipeline — order events enqueue `PrintJob`s; store print agents authenticate with per-tenant keys and claim jobs via `FOR UPDATE SKIP LOCKED` with a 5-minute crash-recovery lease; 42-column receipt rendering rules; manual reprint; mock printer dev server.
- **POS sync:** transactional outbox (`PosOutbox`, enqueued in the same transaction as status writes), 30s worker claiming across tenants then processing inside each row's tenant context, idempotency via `OrderPosMapping`, deferral-without-retry-consumption for out-of-order events, per-tenant encrypted provider credentials (ForeverPOS today; design for pluggable providers).
- **Reporting API:** `/api/reporting/v1` for external BI — per-tenant hashed bearer tokens (token *is* the tenant), IP + per-tenant rate limits, paginated products/categories/inventory-snapshots/orders endpoints, stable prefixed IDs, documented limitations blocks, per-tenant timezone/currency. A **live external consumer exists** (PHYSALIA; see `docs/reporting-api/`), so contract compatibility vs. a versioned break is an explicit spec decision. Known defects to not replicate: a double-wrapped response envelope contradicting the API doc, pagination that under-fills pages under derived payment-status filters, and fabricated payment facts (`paid_at` derived from `updatedAt`) — the rebuild records payment truth instead of deriving it.
- **Content & support:** announcements (store-scoped banners); landing merchandising (featured products, promotion carousel); contact/support messages with enum subjects, one-reply rule, reply-by-email through Make; help page (currently hardcoded contact info — must become tenant settings).
- **Platform admin:** tenant CRUD with one-time machine-token reveal, suspend/activate, token regeneration (currently nested inside tenant admin — must become a separate super-admin plane); custom-domain management is absent (today `Tenant.customDomain` is set by direct DB edit) — the platform plane needs domain add/verify/remove wired to the TLS issuance story; `Tenant.plan` exists but is unenforced (spec must decide plan/quota enforcement).
- **Dormant/incomplete (explicit decisions required):** product reviews (full schema, read-path only; frontend mutations are fake client-side state), `CartItem` table (unused; carts are client-side), refunds (reporting returns an empty envelope), discounts/delivery-fee columns (always 0); a client-side guest sentinel (`web/src/utils/roles.js`, id 999 — a seeded GUEST role exists but there is no backend user row).
- **Ops:** Prometheus metrics + Loki logs (no tenant dimension today — add one), request-ID correlation, health checks, layered compose files, deploy/backup scripts, CI (typecheck gate + vitest + Playwright), migration runbooks. Wildcard-TLS and Caddy on-demand-TLS templates for tenant domains exist but are unwired (`infra/tls/` — the rebuild's infra chapter must solve tenant TLS properly).

## Design failures the rebuild must structurally prevent

These are observed defects of the current system, generalized. For each, your spec must show — by construction, not by promise — why the failure class cannot recur. Verify examples in Phase 0.

1. **Isolation by convention.** One `any`-typed query interceptor is the entire tenant boundary; raw SQL and an unscoped client bypass it; nested `connect`/`connectOrCreate` is documented as un-validated; three data-access idioms coexist; unauthenticated `X-Tenant-ID` overrides work in production; an admin JWT from tenant A unlocks tenant B's aggregates (`isAdminCaller` never tenant-matches); and the fail-closed posture itself hangs on `NODE_ENV`/`VITEST` detection — dev mode passes missing-context queries through with a warning, rate limits vanish under `NODE_ENV=development`, and an in-repo comment says a deployed container runs that way permanently. → The rebuild needs defense-in-depth: database-enforced isolation (e.g., Postgres RLS keyed on a session tenant setting, or schema-per-tenant — evaluate options) *plus* a single scoped data-access path, *plus* isolation tests as a CI gate — and a security posture that never depends on environment-detection hacks.
2. **Magic sentinels.** `storeId 0` means two different things; tenant fallback `?? 1` is hardcoded in auth despite a boot-time default-tenant resolver; slug `app` and subdomain `admin` are reserved by comment, enforced nowhere; sentinels block foreign keys (`UserRole.storeId`, `UiSetting.storeId` have no FK). → Model these concepts as types/rows, not overloaded integers; keep referential integrity intact.
3. **Single-process in-memory state.** Settings TTL caches, module-level caches (one of which — the thermal printer store-name cache — isn't tenant-keyed and leaks tenant A's name onto tenant B's receipts), the in-process event bus, and rate-limit stores all assume one instance. → Every cache/queue/bus decision must state its multi-instance story and its tenant-keying.
4. **Money math without a single owner.** Tax is a hardcoded platform constant; checkout computes totals with tax, but staff edits (`void`/`delete`/`add` item) recompute totals without tax — and void/delete run their multi-step writes outside any transaction; stock is decremented but never compensated on void, cancel, or abandoned payment; refund-on-delete runs after the delete, outside the transaction. → One money/pricing module owns all total computation; inventory movements are ledgered and compensating; state changes + their financial effects are atomic.
5. **Layer violations and duplication.** Controllers query Prisma directly; a service streams HTTP responses; the payment gateway service persists domain rows; driver authorization rules are implemented twice with drift; role/visibility logic is re-derived in at least three frontend components with different definitions; two validation frameworks with two error formats. → One canonical home per rule; authorization decisions centralized and testable.
6. **Shared mutable singleton state.** The delivery fulfillment strategy caches per-request eligibility on a process-wide singleton — two concurrent checkouts can swap addresses. → Statelessness by default; anything stateful must justify its lifecycle.
7. **Frontend god objects and ad-hoc UI.** Eight contexts spread into one `useApp()` object with ~63 call sites; a 645-line kanban component; ~35-prop drilling; six copies of fetch logic; no component primitives (10+ competing button class conventions); 71 global CSS files with ~15 breakpoints; full-collection refetch after every mutation; five independent 60s pollers; `window.location.reload()` on store switch. → The rebuild's frontend chapter must specify state architecture, data-fetching/cache strategy, a real component library, and a realtime approach.
8. **Tenant identity leaking into artifacts.** Hardcoded phone numbers and brand images in the bundle; global Make webhook URLs and API key shared by all tenants with no tenant field in the payload; reporting/print-agent contexts bound only to the default store, hiding multi-store data; metrics/logs without a tenant label. → Every outbound artifact (page, webhook, receipt, export, metric) derives tenant identity from context; integrations are configured per tenant.
9. **Retrofit type dishonesty.** `tenantId` is `Int?` in the Prisma schema but NOT NULL in the database, purely so the interceptor can inject it; business tables have no FK to `tenants`, so deleting a tenant orphans everything. → In the rebuild the type system and schema tell the truth; tenant deletion/offboarding is a designed lifecycle.
10. **Features that lie.** Reviews render optimistic client state that never persists; specialInstructions is collected at checkout and silently dropped; support replies persist metadata but never the reply body (dead `replyMessage` column — the content is lost whenever email delivery fails). → The parity matrix must catch these; the spec finishes or removes them.
11. **Business rules enforced only client-side.** The order-status transition graph exists only in the staff UI — the API lets any EMPLOYEE+ set any status from any status; the delivery kill-switch is checked in the cart UI but never in the server's delivery validation, so a direct API call places delivery orders while delivery is "off"; and roles gate actions but not data breadth — drivers receive the entire order book with every customer's address and phone, filtered client-side. → Every business rule has exactly one server-side owner; the order lifecycle is a real state machine validated on every transition; authorization scopes data visibility, not just endpoints.

## The theming engine (core requirement)

Design this as a first-class subsystem, not a settings page. The scope below is already decided by the product owner — do not re-open it in Phase 1:

- **Design-token architecture:** a complete taxonomy (color, typography, spacing, radii, elevation, motion, component-level variables) with a resolution chain — platform defaults → theme preset → tenant overrides (→ store overrides if Phase-1 questions confirm per-store branding). Semantic tokens over raw values; light/dark as first-class modes of every theme.
- **Curated theme presets:** several professionally designed, distinct presets (not eight shades of one palette). A tenant picking a preset and uploading a logo must get a storefront that looks intentionally designed.
- **Tenant customization, bounded:** colors (with automatic derivation of interaction states, as the current system does with HSL math — generalize it), typography from a curated font set, logo/favicon/imagery, radius/density choices. Guardrails are part of the design: automatic contrast/accessibility enforcement (WCAG AA), so a tenant cannot make an unreadable store.
- **Configurable storefront sections:** the storefront (landing page especially) is composed of section types — hero, promotion carousel, featured products, category grids, announcement banner, rich-text/FAQ — that tenants enable, reorder, and configure. No freeform builder; section contracts keep design integrity.
- **Editing experience:** live preview against the tenant's real catalog, draft vs. published theme states, and rollback. Specify where preview rendering happens and how it is isolated from the live store.
- **Branding beyond the storefront:** transactional surfaces (notification emails via webhook, receipts, customer-facing order pages) consume the same brand identity.
- **Performance:** first paint must be brand-correct with no flash of default theming — the current system races a CSS injection against a 200ms timeout (`web/src/main.jsx`); your design must solve this properly (e.g., server-rendered tokens or per-tenant compiled CSS — any approach must respect the no-managed-cloud constraint), including on custom domains.
- **Versioning & migration:** how token schemas evolve without breaking existing tenant themes.

## Mandated spec structure

1. Executive summary; goals and non-goals
2. Domain model and ubiquitous language (Tenant, Store, catalog, orders, fulfillment, identity)
3. System architecture overview — chosen stack with justification; component and request-flow diagrams
4. **Multi-tenancy architecture** — tenant resolution (domains/subdomains/TLS), isolation enforcement (DB-level + application-level), tenant and store lifecycle (provision → operate → suspend → offboard/export), platform vs. tenant control planes, plan/quota enforcement, machine identity (per-tenant tokens)
5. Data architecture — schema, scoping and integrity rules, money/decimal handling, auditing, inventory ledger, migrations strategy
6. Module/service boundaries — catalog & pricing, inventory, cart/checkout, orders, payments, fulfillment/delivery, notifications, printing, POS sync, reporting, support/content, identity & access; contracts between them; where the current strategy patterns (payments/fulfillment) evolve
7. API design — style, versioning, authn/z, error model, machine APIs (reporting, print agents), webhooks (per-tenant)
8. Frontend architecture — application(s) structure, routing (tenant/store awareness), state and data-fetching strategy, realtime, component library approach
9. **Design system & theming engine** — everything in the theming section above, concretely specified
10. Admin surfaces — storefront, tenant admin, staff ops (orders board, delivery), super-admin console
11. Identity, authorization & compliance — role model, store-scoped permissions, approval gating as per-tenant policy, session/token design
12. Integrations — payments, POS providers, printing, geocoding, notification/webhook delivery, BI/reporting
13. Infrastructure & operations — topology (single-VPS baseline → scale path), caching, background jobs, observability with tenant dimensions, backup/restore, TLS for tenant domains
14. Security & privacy — threat model incl. cross-tenant vectors, secrets, PII handling, rate limiting
15. Testing strategy — including tenant-isolation test gates and theming visual regression; state what the rebuild keeps or replaces of the existing e2e flows, isolation gates, and live-verification suites
16. Migration & cutover — data mapping from the current schema, asset migration, integration re-keying, rollback plan
17. Feature-parity matrix (appendix)
18. Open questions & risks register
19. Decision log — ADR-style entries for every significant choice: context, options, decision, consequences

Chapters 4, 5, 9, and 16 are the load-bearing chapters — give them the most depth. Elsewhere, a short chapter with real decisions beats a long one with hedged ones; brevity is not a placeholder.

## Quality bar

- Every significant decision appears in the decision log with at least two rejected alternatives, each with the specific reason it lost — a reason that would survive the question "then why not do that instead?"
- Every tenant-isolation claim names its enforcement mechanism and layer; nothing isolates "by convention."
- Every requirement is stated testably; every chapter ends with acceptance criteria an implementation plan can be checked against.
- The spec is honest about costs: operational burden, migration risk, and what gets worse in the rebuild (something always does) are stated, not hidden.
- Write for a small team: decisive, opinionated, YAGNI-biased. When in doubt, choose the design that is easiest to delete.
